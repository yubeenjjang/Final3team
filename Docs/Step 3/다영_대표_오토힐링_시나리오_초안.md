# 귀가 경로 대표 오토힐링 시나리오 초안

> 상태: 팀 논의용. 기존 기획서 3.3~3.5, FR-H21~H27 및 API 설계서 A15~A19의 범위 안에서 작성했다. 수치 기준과 구현 여부는 W96 계측·W48 정책 확정 전에 검증해야 한다.

## 제안 결론

대표 장애는 **축제 종료 직후 놀다가의 내부 귀가 경로 조회 처리 지연**으로 둔다. 같은 출발·목적지·수단·시간·통제 조건의 요청이 반복되는 시험에서는 `singleflight_enable`을 후보로 선택한다. 목적지나 조건이 서로 다른 시험에서는 병합을 기각한다. 이 차이를 Diagnosis와 Recovery가 실제 지표를 보고 판단하는 장면이 에이전트의 역할을 보여준다.

12/8 중간발표는 정상 귀가 흐름과 확인된 부하 지표·실패 안내까지만 확실하게 시연한다. 감지→진단→자동 조치→동일 부하 재검증이 아직 완성되지 않았다면 **후속 개발 계획**으로 표시한다. 완성 후 대표 오토힐링 효과는 같은 조건의 B0/B1/A1 시험으로 입증한다.

## 장면 A: 같은 조건의 귀가 조회가 몰림 — 대표 후보

1. **사용자 상황:** 축제 종료 직후 많은 이용자가 같은 축제장에서 같은 역으로 귀가 경로를 조회한다. 현장 인파 자체가 서버 장애는 아니며, 놀다가에 들어온 경로 조회 요청 증가가 직접 원인이다.
2. **장애 재현:** 실제 TMAP·카카오맵에는 부하를 보내지 않는다. 팀이 통제하는 내부 경로 처리 계층과 모의 공급원에서 요청 수·동시성·중복 키 비율을 고정해 지연을 만든다.
3. **감지(코드):** offered RPS, 내부 p95, 큐 길이, 시간 초과·거절, 유효 경로 완료율을 시간창별로 기록한다. 사건 생성 기준은 W48에서 정상 기준을 측정한 뒤 고정한다. `queued`와 `accepted`는 성공이 아니다.
4. **Diagnosis 판단:** A16 지표와 A15 사건을 읽고 `duplicate_ratio`, `unique_route_keys`, `backend_execution_count`, `upstream_p95_ms`, `internal_p95_ms`를 대조한다. 외부 공급원은 정상인데 내부 실행 수와 대기열이 늘고 동일한 `route_key`가 반복되면 **내부 중복 실행이 병목이라는 가설**을 근거와 함께 기록한다. 외부 지연이 주원인이면 이 가설을 채택하지 않는다.
5. **Recovery 판단:** A18의 현재 허용 조치를 읽고 `singleflight_enable`을 선택한다. 정책 코드는 동일 키·저장/병합 허용 범위·상한을 다시 검증한 뒤 실행한다. 에이전트 제안 자체는 실행이나 복구 성공이 아니다.
6. **재검증:** 조치 전후에 **같은 offered load·입력 분포·자원·시간 제한**을 유지한다. 실제 유효 경로 완료율, 경로 도착까지의 p95, 시간 초과·거절률, 큐, 감지부터 정상화까지 시간을 비교한다. 거절을 늘리거나 접수만 빨라진 경우는 성공에서 제외한다.
7. **실패·원복:** 유효 완료율이 개선되지 않거나 거절·시간 초과가 늘면 `rollback`을 기록하고 원래 정책으로 복귀한다. 다른 허용 조치를 검토할 수 없으면 `safe_degrade`로 경로 확인 불가를 안내하고 축제 검색·상세는 유지한다. 이 상태는 경로 복구 성공이 아니다.

## 장면 B: 요청 수는 같지만 목적지가 제각각 — 판단 대조군

같은 규모의 부하에서 목적지와 조건을 달리하여 `route_key` 중복률을 낮춘다. Diagnosis는 내부 지연이 있어도 **중복 실행이라는 근거가 약함**을 밝힌다. Recovery는 `singleflight_enable`을 **기각**하고 내부 큐가 원인일 때만 `bounded_queue_adjust`를 검토한다. 대기열 조정이 지연을 줄여도 유효 완료율이 떨어지거나 거절이 늘면 복구 성공이 아니다. 허용 조치가 적합하지 않으면 `defer` 또는 `safe_degrade`로 끝낸다.

## 에이전트가 실제로 기여한 부분

| 단계 | 담당 | 남길 증거 |
|---|---|---|
| 요청 문맥 | Route | 축제 ID, 경로 요청 ID, 상태, 공급원·시각·실패 코드. 경로 후보 본문은 에이전트 기록에서 제외 |
| 원인 구분 | Diagnosis | 사실/가설/미확인 분리, 내부·외부 지연, 중복 키 분포, 영향 범위 |
| 조치 선택·기각 | Recovery | A18 허용 목록, 선택/기각 이유, 중단·원복 조건 |
| 실행·판정 | 정책 코드 | A19 결정 검사, 실행 이력, 같은 부하 재측정, 최종 상태 |

Route는 사용자 귀가 흐름의 주체다. Diagnosis·Recovery는 장애 사건에서만 실행한다. 모델이 시간 초과·형식 오류를 내면 B1 고정 규칙 또는 안전 종료로 넘기고 사건에 실제 대응 주체를 기록한다.

## 비교 시험과 합격 판정

| 비교군 | 의미 | 관찰할 것 |
|---|---|---|
| B0 | 자동 조치 없음 | 병목과 사용자 피해가 재현되는가 |
| B1 | 사전에 정한 규칙 대응 | 규칙만으로 개선되는 정도 |
| A1 | Diagnosis→Recovery 근거 판단 | 장면 A에서 적합한 조치를 고르고 장면 B에서 부적합한 조치를 기각하는가 |

시험마다 입력 키 분포, 총 요청 수, 동시성, 모의 공급원 지연, 캐시 상태, 처리 자원, 시간 제한을 고정하고 여러 번 반복한다. 분모는 **제공한 전체 요청**으로 둔다. 제한 시간 안에 `ready`와 `completed_valid_route=true`로 검증된 응답만 유효 완료로 센다. 경로 미제공 상태인 `queued`·`processing`·`rejected`·`timed_out`은 별도 집계한다. A1이 B1보다 낫지 않다면 AI 추가 가치가 없었다고 기록한다.

## 팀에서 확정할 항목

1. W96 계측으로 내부 병목 위치와 장면 A/B의 재현 가능한 입력 분포를 확인한다.
2. W48에서 감지 기준, 유효 완료 기한, 반복 횟수와 합격선을 **시험 전에** 고정한다.
3. `route_key`에 어떤 입력·시각·통제 버전을 포함하고, 어떤 공급원 응답의 병합이 허용되는지 정책 코드와 대조한다.
4. 12/8 시연의 실제 완료 범위를 확인한다. 정상 경로·실패 안내·부하 지표까지 확인되면 보여 주고, 자동 전환과 재검증은 구현·시험 결과가 있을 때만 시연한다.
