# 에이전트 도구 인계 (한다영, 2026-11-22)

단일 Festival Agent(설계·구현)와 단일 에이전트 설계서(11/27 제출)에 바로 쓸 수 있게 **도구 계약·호출 대상·상태·실패 처리**를 한곳에 모았습니다. 원문은 API 설계문서 v0.3.3 4·5·7-6절입니다.

## 1. 도구 13개와 지금 부를 수 있는 모의 API
JSON Schema 원본: [`tools/<도구 이름>.json`](tools/) (API 설계문서 4-6에서 그대로 뽑음, 13개). 모의 서버는 `http://localhost:8000/api/v1`([README](README.md)).

| 도구 | 감싸는 API | 모의 | Festival Agent | 비고 |
|---|---|---|---|---|
| `search_festivals` | A02 `GET /festivals` | ✅ | ✅ | 지역 `SEOUL`·`ALL` 등, 기간 겹침 |
| `get_festival` | A03 `GET /festivals/{id}` | ✅ | ✅ | 없는 ID → `FESTIVAL_NOT_FOUND` |
| `get_official_notices` | A07 `GET /festivals/{id}/notices` | ✅ | ✅ | 승인된 공지만 |
| `get_crowd` | A10 `GET /festivals/{id}/crowd` | ✅ | ✅ | 서울만, 그 밖 `unsupported`(실패 아님) |
| `get_facilities` | A08 | ❌ | ✅ | 모의 없음 → 당분간 가짜 응답을 도구 쪽에서 |
| `save_favorite` | A12 `PUT /me/favorites/{id}` | ✅ | ✅ (로그인 대화만) | 비로그인 대화에는 도구를 주지 않음 |
| `request_return_route` | A04 `POST /routes/return` | ✅ | Route | ⚠ 스키마에 `origin`(출발지 변경) 아직 없음 — API 11-1절 14번 |
| `get_route_request_status` | A05 `GET /routes/return/{id}` | ✅ | Route | 헤더 `X-Route-Access-Token` |
| `get_incident`·`get_route_metrics`·`list_allowed_actions`·`propose_recovery_action` | A15·A16·A18·A19 | ❌ | Diagnosis·Recovery | 운영 맥락 전용(챗봇 대화에는 안 줌) |
| `predict_route_delay_risk` | A17 | ❌ | — | 후속(501) |

- 날씨(A09 `/weather`)는 도구 목록에 없습니다. Festival Agent가 날씨를 답해야 하면 도구 추가를 정해야 합니다(API 문서 14절 '새 에이전트 도구' 규칙: 4절 표 + BFCL 문항 검토).
- **ID에 `pattern`을 넣지 않은 이유:** BFCL 평가가 `F01`·`RR02` 같은 가짜 ID를 쓰기 때문(4-6). 실제 형식 검사는 API가 함.

## 2. 도구 공통 출력 (4-5절)
```json
{ "ok": true,  "data": { "…API 응답 본문…" }, "request_id": "req_…", "is_mock": true }
{ "ok": false, "error": { "code": "ROUTE_TIMEOUT", "message": "…", "retryable": true }, "request_id": "req_…" }
```
도구 래퍼가 모의 API 응답을 이 모양으로 감쌉니다. HTTP 오류 본문 `{"error": {...}}`를 그대로 `error`로 옮기면 됩니다. 에이전트는 **`ok`와 `retryable`만 보고** 다음 행동을 정합니다.

| 실패 코드 | retryable | 다음 행동 |
|---|---|---|
| `ROUTE_TIMEOUT`·`TOOL_TIMEOUT` | true | 먼저 `get_route_request_status` 확인 → 아니면 같은 `request_id`로 1회 |
| `ROUTE_UPSTREAM_ERROR`·`RATE_LIMITED` | true | 1회 뒤 '확인 불가 + 공식 안내' |
| `VALIDATION_ERROR`·`ROUTE_INVALID` | false | 사용자에게 다시 물음 |
| `FESTIVAL_NOT_FOUND` | false | 검색 단계로 되돌아감 |
| `FORBIDDEN` | false | 멈추고 이유 안내(우회 금지) |
| 지역 미지원(`status:"unsupported"`) | — | **실패 아님**, '이 지역은 미지원'으로 안내 |

## 3. 챗봇 작업 상태 (A06, 7-6절) — 화면·워커 공통
- 접수 `POST /assistant/query` → 202 `run_id` / 조회 `GET /assistant/runs/{run_id}`
- `run_status`: `queued` → `running` → `succeeded` | `retrying`(LLM 일시 오류, 같은 `run_id`로 1회) → `failed`
- 전체 제한 30초, 워커가 죽어 `running`이 70초를 넘으면 정리 작업이 `failed`로 바꿈(9-1)
- **재시도 vs 새 작업:** 재시도는 같은 `run_id` 안에서 서버가 하고, 사용자가 다시 물으면 새 `request_id` → 새 `run_id`
- 모의 서버 시험: 질문에 "귀가" → 경로까지 성공, "실패" → `AI_AGENT_FAILED`

## 4. 꼭 지킬 규칙 (설계서에 그대로 옮길 것)
1. **경로 내용을 답변·기록에 넣지 않음:** `answer`는 30일 저장이라 TMAP 24시간·카카오 저장 금지에 걸림 → "경로를 찾았어요, 귀가 화면에서 확인하세요" 수준, 경로는 `route_request_id`로만. 체크포인트(7일)·에이전트 입출력 기록에도 `route_candidates`는 빼고 `route_request_id`·`provider`·`route_status`만.
2. **근거 없는 단정 금지:** 반려견 동반·접근성·혼잡 회피는 검증된 근거가 있을 때만(`constraint_status: not_verifiable`).
3. **권한:** 질문 속 "나는 관리자"는 권한이 아님. 운영 도구는 챗봇 대화에 주지 않음.
4. **상대 날짜:** "이번 주말"은 `reference_date` 기준(BFCL 평가는 고정값).
5. 모의 응답(`is_mock: true`)을 실제처럼 단정하지 않음.
