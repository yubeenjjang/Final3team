## 실행 결과

1. `run_tests.sh`에서 001 기본 DDL부터 028까지 적용·되돌리기·재적용, 권한/RLS·사전 중단 조건·백업 복원 시험을 실행했다. 종료 코드 0, `ALL SQL TESTS PASSED`, `AFTER-BACKUP TESTS PASSED`를 확인했다. 각 버전의 시험은 해당 SQL이 다루는 기존 행과 제약을 별도로 검사한다.
2. 별도 빈 DB에서 `migrate.py`가 001~028 **28개를 순서대로 적용**했다. 같은 DB에서 다시 실행하자 적용 이력과 파일 해시를 대조하고 **28개를 모두 건너뛰었다**.
3. 이 별도 DB에 시험용 축제 1건을 넣은 뒤 관리자 계정으로 028→002의 `_down.sql`을 역순 실행했다. 각 파일이 성공한 뒤에만 `migration_meta.schema_migrations`의 해당 번호를 삭제했다. 남은 이력은 001뿐이었고 축제 1건은 유지됐다. `migrate.py`를 다시 실행해 002~028 **27개를 재적용**했고 최종 이력 001~028과 축제 행 보존을 확인했다.

## 실제 TourAPI 응답 16건 추가 시험

- 저장소의 [2026-11-19 실호출 응답](../evidence/responses/) 서울 10건·부산 6건을 `tourapi_snapshot.load_snapshot()`으로 정규화했다. 후보 16건, 제외 0건이었다. 운영 DB의 870건 전체나 최신 공급원 응답은 아니다.
- 새 일회용 DB에 001~028을 적용하고 `tourapi_snapshot.ingest()`로 **16건을 적재**했다. 같은 응답을 다시 넣었을 때 신규 0건·변경 0건이었고 축제·원본 연결 16건이 유지됐다.
- 최초 시험에서는 028→002까지 되돌린 후 003을 재적용할 때 `festivals_image_copyright_needed` 제약 위반으로 중단됐다. 원인은 003 되돌리기가 `image_copyright_type`을 삭제하면서 기존 `image_url`은 남겨, 재적용 시 이미지 주소가 있는 행에 저작권 유형이 없어진 것이었다.
- [003 되돌리기 SQL](003_festival_images_down.sql)에 이미지·썸네일·저작권 정보가 있는 행의 되돌리기를 **사전에 중단하는 조건**을 추가했다. 새 일회용 DB에서 실제 응답 16건을 다시 적재한 뒤 028→004 **25개를 역순 되돌리고**, 003 되돌리기는 예상대로 중단되는지 확인했다. 그 시점의 이미지 16건과 적용 이력 001~003이 유지됐다. 이어 004→028 **25개를 재적용**했고 축제 ID·이름·기간·원본 ID·체크섬 16건이 전후 동일했다.
- 보호 조건을 반영한 `run_tests.sh` 전체 SQL·백업 복원 시험도 종료 코드 0으로 재실행했다. 위의 [전체 SQL 시험 로그](results_2026-11-25_w17_yubeen.log)는 이 최종 실행 결과다.

## 실행 환경 보완과 제한

- Windows Git Bash에서 `backup_long_term.sh`의 CRLF를 Docker 컨테이너에 그대로 넘기면 Bash가 실패했다. 시험 실행기가 CRLF를 제거해 전달하도록 수정했다.
- Git Bash가 컨테이너의 `/tmp`를 Windows 경로로 변환해 `pg_dump`가 실패했다. 시험 실행기에서 `MSYS_NO_PATHCONV=1`을 설정했다. 수정 후 전체 시험이 완료됐다.
- 028→002 전체 역순 시험에서 보존을 직접 확인한 행은 시험용 축제 1건이다. 실제 TourAPI 16건을 넣은 시험은 028→004까지만 안전하게 되돌렸고 003에서는 의도적으로 중단했다. 다른 기존 데이터 유형은 SQL별 시험의 시드·보존 검사를 근거로 한다. 009 되돌리기에도 데이터 손실·중단 조건이 있으므로 운영 DB에서 같은 순서를 실행해도 무손실이라고 판단하지 않는다.
- 001의 `_down.sql`은 없다. 001 이전으로 복구하려면 검증된 백업 복원이 필요하다.
