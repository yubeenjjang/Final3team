# 놀다가 기능 시나리오 — 팀 공유용 초안

> 기준: `Docs/Step 1/놀다가_기획서.md`의 서비스 범위와 요구사항, 2026-11-20 팀장 화면·가입 정보 결정, 첨부된 `놀다가_API키_지역범위_정리.md`와 지도 화면 예시. 이 문서는 팀원이 **사용자 행동 → 화면 반응 → 시스템 처리 → 예외 상황**을 함께 이해하기 위한 요약이다. API·DB의 확정 명세나 구현 완료 보고서는 아니다. 기존 기획서·API·DB 문서와 달라진 내용은 7절에 표시했다.

## 1. 앱을 한 문장으로 설명하면

사용자가 전국 축제를 찾고, 축제 정보와 필요한 현장 정보를 확인한 뒤, 검증된 데이터에 근거해 **가는 길과 귀가 방법을 판단**하도록 돕는 서비스다. 취향 추천과 동행·친구·채팅은 축제 전후의 경험을 넓힌다. 운영자는 귀가 조회 장애를 감지하고, 허용된 복구 조치가 실제로 효과가 있었는지 확인한다.

## 2. 먼저 구분할 세 가지 범위

| 구분 | 무엇을 보여주거나 구현하나 | 완료 판단의 핵심 |
|---|---|---|
| **첫 시연** | 전국 여러 축제 검색·상세 → 기본 귀가 경로 조회 → 내부 모의 부하 → 진단·복구·같은 부하 재검증 | 경로가 실제로 제공됐는지, 장애 후에도 같은 조건에서 개선됐는지 확인 |
| **최종 필수 기능** | 첫 시연 범위에 가는 길, 현장 정보, AI 챗봇·방문 코스·RAG, 계정·관심, 맞춤 추천, 동행·친구·채팅, 데이터 수집·관리 등을 확장 | 각 기능의 원천·권한·오류·미지원 상태까지 검증 |
| **선택·보류·제외** | 고급 경로 비교·후기·상권 확장 등은 선택. 물품보관함·약국은 보류. 예매·결제·개인 위치 추적은 범위 밖 | 팀 결정 없이 필수 기능으로 간주하지 않음 |

**주의:** 첫 개발에서 쓰는 모의 경로는 서비스의 실제 길찾기 완료를 뜻하지 않는다. 실제 경로 연동·공급원 전환은 별도로 검증해야 한다.

## 4. 기능별 시나리오

### S01. 축제 탭·전국 축제 탐색·상세 — 탐색·상세는 첫 시연 필수

1. 사용자가 **축제 탭**을 열면 ① 나만을 위한 맞춤형 축제 ② 현재 인기 있는 축제 ③ 전체 축제 리스트 ④ 새로 올라온 축제 순서로 본다. 이는 **개별 축제의 상세 화면**과 다른, 축제 탐색 화면이다.
2. **나만을 위한 맞춤형 축제:** 저장된 취향을 바탕으로 추천 축제를 **리스트 형식으로 연속해서** 보여준다. 온보딩을 건너뛴 사용자에게는 ‘맞춤형 축제 찾아보기’ 배너를 보여주고, 누르면 취향 카드 5장으로 다시 들어간다.
3. **현재 인기 있는 축제:** 실제 조회·관심 지표를 기준으로 인기 축제를 보여준다. 집계가 부족하면 임의 순위를 만들지 않는다.
4. **전체 축제 리스트:** 전국 공개 축제의 일부를 무작위로 섞어 보여준다. 새로고침마다 순서가 계속 뒤집히지 않도록 하루 또는 세션 단위의 고정 시드를 쓴다. 상단의 작은 **‘전체보기’**를 누르면 지역별 축제 리스트로 이동하고 지역·기간·상태 등으로 찾을 수 있다.
5. **새로 올라온 축제:** 행사 개최일이 아니라 서비스에 처음 공개된 날짜(`published_at`)가 최신인 축제를 보여준다.
6. 사용자가 축제 카드를 누르면 **개별 축제 상세 화면**으로 이동해 일정·장소·소개·입장료(원본에 있을 때)·출처·갱신 시각을 본다. 좌표 없는 축제는 목록에는 남겨도 지도 마커는 표시하지 않는다.
7. 목록과 상세는 수집·검증된 DB 자료에서 제공한다. 축제 탭을 열 때마다 외부 축제 API를 직접 호출하는 흐름으로 만들지 않는다.

**연결:** 축제의 `festival_id`와 장소 좌표는 귀가 화면의 출발 위치 초깃값으로 이어진다. 사용자는 S06에서 출발 위치를 바꿀 수 있다. 관련 요구사항: FR-F01/F10/F15, FR-D02/D06~D11.

### S02. 첫 로그인 취향 스와이프·추천 미리보기·재진입 — 최종 필수

1. 회원가입 후 **앱을 처음 사용할 때** 축제 취향을 쉽게 고를 수 있도록 스와이프 화면을 보여준다. 앱 첫 경험을 돕는 **마케팅·온보딩 화면**이며 이후 앱 사용을 위한 필수 절차는 아니다. 카드는 **가족과 함께 / 친구와 함께 / 연인과 함께 / 반려견과 함께하는 축제 / 혼자 즐기기**의 5가지다.
2. 카드를 넘겨 보다가 원하는 취향을 직접 선택한다. 여러 취향을 함께 고를 수 있다.
3. 취향 선택을 마치면 첨부한 이미지처럼 **선택 완료 카드**를 보여준다. 선택한 취향을 요약하고 **‘맞춤 축제 보러 가기’**와 **‘놀다가 홈으로 가기’** 두 선택지를 제공한다.
4. **‘맞춤 축제 보러 가기’**를 누르면 추천 축제 **3~4개를 한 장씩 스와이프**하며 먼저 볼 수 있다. 각 축제 카드에는 **‘축제 상세보기’**가 있어 해당 축제 상세로 이동할 수 있다. 카드를 끝까지 보면 **메인 홈 화면으로 가는 버튼**을 보여준다. ‘놀다가 홈으로 가기’를 누르면 추천 미리보기를 거치지 않고 바로 메인 홈으로 간다.
5. 메인 홈의 축제 탭에서는 ‘나만을 위한 맞춤형 축제’에 **추천 축제가 세로 리스트로 이어져** 나온다. 이는 첫 이용 때의 **3~4장 추천 스와이프 미리보기**와 다른 화면이다. 추천은 승인된 공개 축제와 검증된 태그·날짜 등을 이용한 **규칙 기반 계산**이다.
6. 취향 선택 중 **건너뛰기**를 누르면 바로 **메인 홈 화면**으로 이동한다. 이후 축제 탭의 맞춤 추천 자리에는 취향 선택을 다시 안내하는 배너를 둔다. 배너를 누르면 같은 5장 취향 화면이 열린다.
7. 선택을 마친 사람은 매 로그인 때 같은 화면을 반복해서 보지 않는다. 마이페이지의 **‘나의 축제 취향’**에서 취향을 바꿀 수 있고 변경 후 추천을 다시 계산한다.
8. 취향을 건너뛰거나 추천이 실패해도 인기·전체·최신 축제는 이용할 수 있다. 추천됐다는 이유로 관심 축제에 자동 등록하지 않는다. 추천할 만한 축제가 3개보다 적으면 실제 있는 축제만 보여주고 없는 축제를 채워 넣지 않는다.

**구분:** 추천은 ‘어떤 축제를 갈까?’를 돕는다. S05의 AI 방문 코스는 ‘선택한 축제에서 무엇을 할까?’를 돕는다. 관련 요구사항: FR-REC01~16.

### S03. 계정·프로필·마이페이지 — 최종 필수

1. 사용자는 회원가입 때 **닉네임·나이·성별**을 입력한다. 현재 API 초안의 이메일·비밀번호 로그인도 유지하는 전제로 적었으며, 필수 여부·나이 입력 방식·성별 선택지는 API·DB 문서에 반영할 때 확정한다.
2. 앱 첫 이용에서는 S02의 취향 화면을 보여준다. 건너뛰면 메인 홈으로 이동한다. 이후 로그인할 때마다 같은 화면을 반복해서 보여주지 않는다.
3. 첨부한 마이페이지 예시를 기준으로 **프로필·프로필 수정, 나의 축제 취향·취향 변경, 내 동행·동행 채팅방, 내 동행 활동, 계정 정보/비밀번호 변경, 공지사항·이용약관, 로그아웃**을 보여준다.
4. **동행에 신청할 때** 작성자에게 신청자의 닉네임·나이·성별을 보여줘 승인 여부를 판단할 수 있게 한다. 다른 사용자의 일반 프로필이나 친구 검색 결과에는 나이·성별을 자동 공개하지 않는다. 타인의 취향과 개인 동행 내역도 볼 수 없다.

**로그인 범위:** 로그인 없이 이용할 수 있는 기능은 추후 결정한다. 동행 신청·친구·채팅처럼 계정과 연결된 기능은 사용자 확인과 해당 권한 검사가 필요하다. 관련 요구사항: FR-A01~04/A08, FR-COM22/24.

### S04. 지도 탭과 축제 현장 정보 — 전국 축제 지도는 첫 시연 필수

1. 사용자가 **지도 탭**을 열면 여러 지역의 축제를 마커로 보고, 지도를 움직이거나 축제를 선택해 해당 축제의 정보로 이동한다. 축제 탭 목록과 지도는 같은 축제 ID를 사용한다.
2. 첨부한 화면 예시처럼 상단에 **AI 챗봇 질문창**, 교통·맛집/관광·편의/안전 분류와 화장실·병원 등 세부 필터, 지도와 주변 시설 목록을 배치하는 방향이다. 화면 예시의 수치·장소는 실제 데이터나 확정된 UI 명세로 취급하지 않는다.
3. **전국 공통 정보:** 축제 목록·상세/이미지, 지도·장소 검색, 가는 길·귀가, 날씨, 화장실·주차장 **위치**·병원/응급실·확인된 자전거 존/택시 승강장, 교통 돌발, 버스 도착, 방문 집중 예측·지역 관광 수요를 공급원 지원·검증 범위에서 제공한다. 서울 버스와 서울 밖 TAGO처럼 내부 공급원은 달라도 화면 항목은 같다.
4. **서울만 제공하는 정보:** 실시간 구역 혼잡도, 지하철 실시간 도착, 공영주차장 빈자리 수(선택 기능), 버스 차내 혼잡이다. 서울 밖에서는 값 대신 **‘이 지역은 아직 지원하지 않아요’**를 보여준다. 지하철역·주차장 위치나 버스 도착처럼 지원되는 기본 정보까지 함께 숨기지 않는다. 서울 TOPIS 통제는 전국 경찰청 교통 돌발에 덧붙이는 지역 정보다.
5. 축제 상세에서도 해당 축제의 현장 정보를 볼 수 있게 연결한다. 지도에 표시할 수 없는 데이터는 목록·텍스트 안내로 제공할 수 있다. 출처·관측 시각·지원 지역을 표시하고, 오래된 정보·미지원·공급원 오류·미검증을 구분한다. 부산 축제에 서울 혼잡 값을 대신 붙이지 않는다.

**범위:** 물품보관함·약국 지도는 현재 보류다. 주차 잔여 면수는 선택 기능이다. 관련 요구사항: FR-F01~05/F09~18.

### S05. AI 챗봇·방문 코스·공식 안내 RAG — 최종 필수

1. **모든 페이지 상단**에 AI 챗봇에 질문할 수 있는 채팅 검색창을 둔다. 사용자는 앱의 어느 기능에 대해서든 자연어로 물어볼 수 있다. 예: ‘이번 주 부산 축제 보여줘’, ‘이 축제 주변 화장실은?’, ‘친구 신청은 어떻게 해?’, ‘여기서 서울역까지 어떻게 돌아가?’
2. 챗봇은 질문이 **앱 사용법**인지, **실제 축제·현장·경로 데이터 조회**인지 구분한다. 전자는 확인된 앱 기능 안내로 답하고, 후자는 필요한 내부 API·공식 안내 도구를 사용해 답한다. 아직 구현되지 않았거나 지원하지 않는 기능은 가능하다고 말하지 않는다.
3. 가족·연인 등 명시한 조건을 반영해 실존 장소와 운영 시간을 확인한 방문 코스를 제안한다.
4. 공식 FAQ·운영 공지는 승인·유효기간·축제 ID를 확인해 검색하고 출처를 표시한다. 실시간 교통·혼잡을 오래된 RAG 문서만으로 단정하지 않는다.
5. 근거가 없으면 ‘확인 불가’로 답한다. AI가 없는 경로·장소·통제를 지어내면 결과를 차단한다. 관심 저장·친구 신청·채팅 전송·관리자 조치처럼 **권한과 실제 데이터 변경이 필요한 행동**은 별도 API·인증·사용자 확인 없이 챗봇 답변만으로 실행하지 않는다.

**Agent 5개:** Supervisor(요청 조정), Festival(축제 확인), Route(경로 해석), Diagnosis(장애 진단), Recovery(복구안 판단). **챗봇은 별도의 여섯 번째 Agent가 아니라 사용자 접점**이다. 관련 요구사항: FR-C01~09, FR-P01~03, FR-K01~05.

### S06. 축제 가는 길·귀가 경로 — 귀가는 첫 시연 필수, 가는 길은 최종 필수

1. **가는 길:** 사용자가 출발지를 입력하면 축제장까지의 경로를 요청한다.
2. **귀가:** 사용자가 귀갓길 화면에서 **출발 위치와 도착 위치를 직접 선택**하고 이동 조건을 입력한다. 축제 상세에서 들어오면 축제 장소를 출발지 **초깃값**으로 채우되 사용자가 바꿀 수 있게 한다. 이 변경은 현재 A04의 `festival_id` 출발점 계약과 달라 API·DB 재설계가 필요하다.
3. API는 경로 요청을 접수하고 `route_request_id`를 발급한다. 사용자는 `queued`(대기), `processing`(처리 중), `ready`(검증된 경로) 또는 실패 상태를 확인한다.
4. 검증된 경로가 있을 때만 후보·교통수단·출처·조회 시각·확인 가능한 제한 조건을 표시한다. 대기열 접수나 워커 작업 종료 자체는 경로 제공 성공이 아니다.
5. 경로가 없거나 공급원이 실패하면 원인을 구분하고 재조회 또는 공식 안내를 제시한다. 확인되지 않은 접근성·운행·통제 상태를 보장하지 않는다.

**공급원:** 1차 TMAP, 실패 시 2차 카카오맵을 선정했다. `Docs/Step 2/evidence/`에 개별 실호출 증빙이 있지만 앱의 경로 연동·자동 전환·저장 조건 검증이 완료됐다는 뜻은 아니다. 카카오맵 경로 본문은 DB·캐시·로그에 보관하지 않는다. 모의 경로는 `is_mock=true`로 명확하게 표시한다. 관련 요구사항: FR-R06/R08~19, FR-R12.

### S07. 동행 모집·승인·동행방 — 최종 필수

1. 사용자는 **동행 찾기 게시판**에서 축제별 모집 글을 찾아본다. 모집 글 작성자는 축제, 미래의 만남 시각, 조건, 추가 모집 인원, 메모를 입력한다.
2. 글을 만들면 작성자만 들어간 동행방이 생기고 만남 장소는 ‘미정’이다.
3. 신청 화면에서 **닉네임·나이·성별이 모집 글 작성자에게 보인다는 사실**을 미리 알린다. 신청 후에는 작성자에게만 그 정보를 보여주며, 작성자는 승인하거나 거절한다. **승인된 사람만** 동행 채팅방에 들어가고, 동시 승인으로 정원을 초과하면 안 된다.
4. **동행 채팅방은 친구 채팅방과 별개**다. 승인된 동행 참여자끼리 메시지를 주고받는다. 작성자가 만남 장소를 확정·변경하면 방 카드·시스템 메시지·앱 내 알림에 반영한다.
5. 모집 글 작성자는 **동행 채팅방에서 ‘동행 종료’**를 누를 수 있다. 종료 즉시 모든 참여자는 메시지를 보내지 못한다. **종료 시각으로부터 3일 뒤 채팅방은 목록에서 자동으로 사라지고 다시 들어갈 수 없다.** 저장된 메시지의 삭제 범위는 구현 전에 정한다.
6. 동행방 상단의 **점 3개(⋯)** 메뉴에서 참여자는 **‘채팅방 신고하기’** 또는 **‘작성자 신고하기’**를 선택한다. 신고 사유를 메시지로 작성해 전송하면 관리자에게 전달된다.

**권한:** 미승인자는 방 메시지와 정확한 만남 장소를 볼 수 없다. 관련 요구사항: FR-COM01~11/18~21.

### S08. 친구·사용자 채팅·알림 — 최종 필수

1. 사용자가 **친구 닉네임을 검색**해 친구 요청을 보낸다. 상대가 요청을 수락해야 친구가 된다. **동행 참여만으로 친구가 되지는 않는다.** 닉네임 중복과 차단 관계도 검색·신청 단계에서 구분한다.
2. 수락된 친구는 **친구 목록**에서 볼 수 있다. 친구 정보에는 **‘1:1 채팅’** 버튼이 있고, 누르면 그 친구와의 1:1 채팅방으로 들어간다.
3. 여러 친구와 대화하려면 별도의 **‘채팅방 만들기’**를 누르고 친구 여러 명을 초대한다. 초대받은 친구는 수락한 뒤 단체방에 입장한다.
4. 친구 삭제·차단·퇴장·방장 승계에 따라 메시지 전송과 구독 권한을 다시 검사한다.
5. 동행 채팅과 친구 채팅은 방 종류·입장 권한·보존 정책을 분리한다. 채팅 목록에서는 전체·동행방·친구 채팅을 구분한다. 신청·승인·친구 수락·장소 변경 등은 앱 내 알림과 읽음 상태로 제공한다.

**구분:** 이 채팅은 **사용자 간 대화**다. S05의 AI 챗봇과 섞지 않는다. 관련 요구사항: FR-COM12~24.

### S09. 후기와 기타 편의 기능 — 선택 구현

- 로그인 사용자가 축제 후기를 작성·조회하고 본인 글을 수정·삭제한다.
- 분실물 센터·미아보호소·일행 만남 장소는 확인된 공식 안내가 있을 때 제공한다.
- 주변 맛집·상권·관광지, 고급 경로 비교, 코스 수정은 채택한 범위에서 확장한다.

관련 요구사항: FR-U01~04, FR-S01~04, FR-F12, FR-R01~05, FR-P02.

## 5. 사용자에게 보이지 않는 운영 시나리오

### O01. 축제 데이터 정기 수집·검토

1. 정기 작업이 승인된 공급원에서 축제 데이터를 가져온다. 공급원별 지원 지역과 수집 시도·성공 시각, 처리 건수, 오류를 기록한다.
2. 제목·기간·장소·좌표·출처를 공통 형식으로 바꾸고 누락·날짜 역전·좌표 오류·중복을 검사한다. 원본 출처와 변경 이력도 연결해 둔다.
3. 검증된 변경만 공개 축제 목록에 반영한다. 공급원 간 날짜·장소·취소 상태가 충돌하거나 중복 판단이 불확실하면 검토 대기 목록에 넣는다.
4. 관리자는 수집 작업과 검토 대기 건을 확인하고 승인·반려하거나 수정한다. 공급원 장애 중에는 마지막으로 검증된 정보를 제공하고 갱신 지연을 표시한다.
5. 관리자가 축제를 직접 등록·수정하는 기능을 적용할 경우에도 게시 전 검증과 변경 이력을 남긴다.

**설계 연결:** API A23~A24, A55~A56(적용 시); DB `data_sources`, `ingestion_jobs`, `festival_sources`, `festival_review_queue`, `festival_change_history`, `festivals`. 관련 요구사항: FR-D01~14, FR-O09~10.

### O02. 공식 공지 등록·승인

1. 공식 공지 기능을 적용하면 관리자가 출처·대상 축제·적용 기간을 확인해 공지를 등록한다.
2. 수정과 승인·반려를 이력으로 남긴다. 미승인 공지는 사용자에게 공개하거나 경로 판단의 확정 근거로 사용하지 않는다.
3. 승인된 공지가 변경되거나 기간이 끝나면 공개 상태와 경로 판단에 쓰이는 정보도 다시 확인한다.

**설계 연결:** API A52~A54(적용 시); DB `official_notices`, `notice_events`. 관련 요구사항: FR-O06, FR-D05.

### O03. 귀가 조회 지표·장애 감지

1. 백엔드는 귀가 조회의 유입 요청 수, 완료 수, 응답시간, 대기열, 오류·거절, 중복 요청과 **기한 내 유효 경로 제공률**을 측정한다. 요청 접수나 ‘확인 불가’ 안내를 실제 경로 제공 성공으로 세지 않는다.
2. 정해 둔 기준을 벗어나면 사건을 만들고 발생 시각·장애 영역·현재 상태를 기록한다. 상태 변경은 별도 이력으로 남긴다.
3. 운영자는 시간대별 지표와 사건 목록·상세를 조회해 어떤 요청과 상태 변화가 있었는지 확인한다.

**설계 연결:** API A14~A16; DB `route_query_metrics`, `incident_logs`, `incident_events`. 관련 요구사항: FR-H01~03, FR-O01~02.

### O04. 진단·허용 조치·재검증

1. Route 맥락과 계측 결과를 받은 Diagnosis Agent는 확인된 사실·가설·미확인을 구분한다. Recovery Agent는 현재 허용된 조치와 상한을 조회한 뒤 조치를 제안·기각하거나 보류한다.
2. 백엔드 정책 코드는 실행 직전에 권한, 조치 조건·상한, 공급원 저장 정책을 다시 검사한다. **Agent의 제안만으로 조치가 실행됐다고 기록하지 않는다.**
3. 실행한 조치와 실패·재시도·해제 여부를 남기고, 같은 요청량·입력 분포·자원 조건에서 전후 유효 경로 제공률·지연·오류를 비교한다.
4. 효과가 없으면 성공으로 기록하지 않고 원복하거나 안전하게 중단한다. 운영자는 진단→결정→정책 검사→실행→재검증의 이력과 최종 결과를 확인한다.

**결과 구분:** 정상 회복, 검증된 캐시, 검증된 대체 공급원, 제한된 기능 상태, 해결되지 않음. **설계 연결:** API A15, A18~A19; DB `incident_diagnostics`, `agent_runs`, `recovery_plans`, `recovery_attempts`, `incident_outcomes`. 관련 요구사항: FR-H04~27, FR-O02~05.

### O05. 통제된 부하 시험 — 첫 시연 핵심

1. 권한이 있는 운영자가 **시험 환경의 팀 내부 모의 경로 처리 계층**에만 동시 요청을 보낸다. TMAP·카카오맵 등 외부 공급원에는 부하를 주지 않는다.
2. 동일한 입력·부하·자원 조건에서 B0(기본), B1(규칙), A1(Agent)을 비교한다. 시험별 진행 상태와 구간별 지표를 남기고, 필요하면 운영자가 즉시 중단한다.
3. 시험에서 사건이 발생하면 해당 사건과 결과를 연결한다. 사건이 발생하지 않은 시험도 시험 자체의 상태와 지표를 확인할 수 있게 한다.
4. 전후 지표와 최종 결과를 확인해 개선 여부를 판단한다. 시험 중 중단·실패한 경우도 그대로 기록한다.

**설계 연결:** API A20~A21, A31; DB `load_simulations`, `route_query_metrics`, `incident_logs`. 관련 요구사항: FR-O03, FR-H21~23.

### O06. 공급원 데이터 보존·정리

1. 경로 공급원별 저장 조건을 확인한 뒤 결과를 처리한다. **카카오맵 경로 본문은 저장하지 않고**, TMAP 경로 데이터는 허용된 범위와 기간 안에서만 보관한다.
2. 만료된 임시 데이터와 캐시는 정리 작업으로 삭제한다. 운영 지표와 사건 기록에는 경로 본문이나 불필요한 개인 위치 정보를 복사하지 않는다.
3. 정리 결과와 실패를 확인해 만료 데이터가 계속 남지 않도록 한다.

**설계 연결:** DB 설계서 7-0 보존·만료 정책, API 설계서 공급원별 저장 정책.

## 6. 모든 기능에 공통으로 적용할 표현·권한 원칙

- **실제 / 모의:** 시험 데이터는 `is_mock`과 화면 문구로 구분한다.
- **확인된 정보 / 미확인 정보:** 출처·시각·지원 지역을 함께 표시한다. 지원하지 않는 지역은 다른 지역 값으로 채우지 않는다.
- **요청 접수 / 결과 완료:** `queued`는 경로 제공 성공이 아니다.
- **공개 / 본인 / 관리자:** 공개 축제 조회와 개인 취향·관심·채팅·운영 화면은 접근 권한이 다르다.
- **안전 보장 금지:** 혼잡 자료나 AI 답변을 개인의 안전, 무장애 이동, 실제 만남 보장으로 표현하지 않는다.
- **외부 공급원 제한:** 경로·개인 장소·메시지는 각 저장·보존 정책을 따른다. 특히 카카오맵 경로 본문을 저장하지 않는다.
- **부분 장애:** 추천·챗봇·외부 데이터 중 하나가 실패해도 가능한 기본 축제 탐색은 계속 제공한다.

| 회원가입·동행 신청 | A32 요청에 닉네임·나이·성별 추가, 닉네임과 기존 `display_name`의 관계, 나이 입력·갱신 방법과 성별 선택지. 신청 시 작성자에게 보여줄 항목·고지·권한·신청 취소 후 처리 정책 |
| 지도 지역 범위 | 전국 공통 원천과 서울 전용 4개 정보의 `coverage`·`unsupported` 응답, 개별 공급원의 실제 지원 지역 확인. 주차 빈자리 등 기획서의 Could 기능은 지역 지원 여부와 별개로 채택 결정 필요 |
| 귀가 출발점 | 기존 A04는 축제 장소를 출발점으로 사용한다. 사용자 선택 출발 위치를 허용하려면 요청 필드·축제 연계·검증·DB 기록·경로 저장 정책 변경 필요 |
| 화면·챗봇 | 메인 홈·축제 탭·지도 탭·귀갓길·마이페이지의 이름과 이동, 상단 질문창의 모바일 배치, 앱 사용법 답변의 근거, 챗봇의 조회·행동 권한 경계 |
| 친구·채팅 | 닉네임 중복 시 식별 방법, 친구 신청·수락·차단, 동행방과 친구방의 멤버 권한·보존 정책 |
| 추후 결정 | 비로그인 이용 범위, 탈퇴의 상세 흐름. 동행방 신고의 관리자 처리 방식 |
| Auto-Healing | 부하 기준선, 허용 조치, 발동·중단 기준과 같은 조건의 재검증 |

이 문서의 시나리오는 **제품에서 해야 할 일**을 설명한다. 실제 일정과 담당은 WBS를 따른다. 위 변경에 영향을 받는 정확한 필드와 테이블은 API·DB 설계 문서에서 업데이트해야 한다. 나이·성별을 추천 계산에 자동 사용하거나 공개 프로필에 노출하는 것으로 해석하지 않는다. 첨부 지역 범위 문서의 ‘크롤링’ 표현은 기존 기획서의 **웹 크롤링 제외** 결정을 바꾸지 않는다.
