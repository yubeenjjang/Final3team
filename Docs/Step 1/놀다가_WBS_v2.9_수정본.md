> 주제: 1번 — 멀티 에이전트 기반 장애 예측·자가 진단·자율 복구(Auto-Healing)  
> WBS 작성: R06 신유빈 · 기술 검토: R03 권오현  
> 서비스: AI 안심 귀가 특화형 전국 축제 플랫폼 · 축제의 시작부터 마지막 귀갓길까지 연결하는 AI 서비스

**이번 개정의 적용 기준:** 전국 축제 지도·검색·상세는 기본 핵심, AI 안심 귀가는 대표 차별화 기능이다. 대표 기술 시연은 **내부 귀가 경로 조회의 동시 요청 지연·과부하 → 진단·복구 → 동일 부하 재검증**이다. 서울 혼잡 API 장애는 보조 시험으로 둔다. 사용자 실시간 채팅·네트워크 자체 단절·예매/자체 결제는 이번 구현 범위에서 제외한다.

**기획서 v2.8 연계 결정(11/18):** 운영 관계형 DB는 Supabase PostgreSQL로 확정한다. Supabase Auth는 본문에 채택/미정 표기가 혼재하므로 W05·W16에서 결정 근거를 확인해 맞춘다. 실제 DB 생성·RLS·마이그레이션·배포는 별도 확인 대상이다. `03_API_설계문서.md` v0.1의 A01~A24는 전체 설계·구현 대상에 포함하되 문서의 1차·최종·보조·후속 단계와 WBS의 필수·선택 우선순위를 유지한다. 범위 포함을 11/20 전체 구현 완료나 선택 기능 자동 채택으로 해석하지 않는다.

아래 변경 일정·배정은 팀 검토용 계획이고 실제 수행·완료를 뜻하지 않는다. 첨부 WBS가 기준으로 삼은 기획서 v2.8의 범위·DB 플랫폼 결정을 유지한다. 이번 개정에서 직접 확인한 자료는 첨부 WBS와 피드백이며, 기획서/API·DB 초안 원본·대시보드·팀 키·API 응답·팀원별 가용 시간은 별도 확인 전이다.

## 2. 일정 관리 규칙

1. **상태 갱신:** WBS 실제 진행표·실제 진행 간트의 갱신 담당은 R06 신유빈으로 확정한다. 각 담당자는 작업일 17:00까지 이슈에 실제 수행일·결과 링크·현재 상태를 갱신하고, R06은 17:30까지 이를 WBS에 반영한다. R01은 범위·버전·대시보드 일치를 확인하고, 검토자는 결과 링크·검토일·판정을 남긴다. 지연에는 원인·영향 작업·변경 예정일을 함께 적고, 금요일 17:30에 주간 실적을 정리한다. 갱신 시각은 팀 확인 전 계획안이다. R01은 11/19 10:00까지 담당별 수업/회의 충돌과 R06 취합 소요를 확인하고 W08에 합의 시각·시행일·기록 링크를 남긴다. 충돌 시 같은 작업일 내 새 마감과 대리 취합자를 정해 WBS·기획서 운영 규칙을 함께 수정하며, 확인 전에는 17:00/17:30을 운영 목표로만 표시한다.
2. **완료·제출:** 필요한 검토와 테스트를 통과해야 완료로 표시한다. 실제 API 연결은 임시 데이터만으로 완료 처리하지 않는다. 문서 작성·검토와 실제 제출·접수를 구분해 확인한다.
3. **진행률:** 검토·시험·해당 제출 확인까지 끝난 **필수 완료 수÷103×100**으로 계산한다. 전체 111개 중 선택·조건부·후속 8개(W40·W43·W85·W107·W108·W109·W110·W111)는 분모에서 제외한다. W111 일반 트래픽 고도화와 달리 최소 귀가 부하 재현·계측(W96), 실제 조치 구현·비교 검증(W48~W52·W106)은 필수다. 선택 작업은 12/04까지 채택/미채택/보류와 담당·공수·일정·시험을 함께 결정하고, 필수 승격 시 기준일과 분모 변경을 기록한다. 현재 증빙을 확인하지 못했으므로 확정 완료 수·진행률은 산정 보류한다.
4. **선행·작업량:** 필요한 결과물을 전달받은 뒤 확인한 범위부터 후속 작업을 시작한다. 예상 작업시간·검토 시간·실제로 일할 수 있는 시간은 기존 작업 이슈나 회의록에 기록한다. 일이 몰리면 분담하고, 그 결과를 WBS의 담당·산출물·일정에 반영한다. 전국 플랫폼·귀가 처리·W96·W48~W52가 우선이다. R03·R06의 API/DB·수집·귀가·부하 작업 중첩과 검토 시간을 먼저 확인하고, 후순위 현장/선택 기능은 일정 영향을 확인해 조정한다. 주말 작업·코어타임·부재 사전 공유·회의록/결정 기록 담당은 11/18까지 팀에서 협의하는 계획으로 둔다(R01·R06 정리). 합의 전 주말을 기본 공수에 넣지 않는다.
5. **휴일:** 주말·12/25·01/01을 작업일에서 제외한다. 기본 작업일은 총 38일이며, 추가 휴강·개인 휴가는 확인 후 반영한다. 12/24 배포 이후에는 새 기능보다 문제 수정·재시험·제출 준비에 집중한다.

W48은 12/02 기존 예비 자료로 정책 틀을 준비하고 W96의 12/03 계측 중간본을 받아 구체화한다. 12/04 오전 W48 정책 결정표 초안을 W44에 전달하고, W96의 12/04 기준선·후보 효과 검토본을 확인한 뒤 12/04 오후 W48을 확정해 W44에 다시 전달한다. W96 후보 시험과 W51 최종 자동 복구 시험을 구분한다. 최종 시험은 **조치 초기 OFF → 지연 감지 → 원인 구분 → 허용 조치 선택 → 코드 검사/실행 → 같은 부하 재검증 → 성공 또는 중단/미해결 기록** 순서로 추적 가능해야 한다. B1은 정해진 규칙으로 감지 후 실행, A1은 Agent가 선택 후 같은 실행기를 사용한다. 사전 ON 요청 묶기는 후보 효과 자료로만 별도 기록한다.

B0(복구 없음)·B1(규칙)·A1(Agent)은 동일 요청 입력/수·offered RPS·동시수·지속시간·seed·분포·목적지 중복률·자원·외부 지연 조건·초기 캐시를 맞춘다. 반복 키/목적지 상이·혼합/고유 키와 burst/지속 부하, cold/warm은 따로 비교한다. 제공 부하는 클라이언트에서 고정·측정하고 큐 진입/거절 요청도 분모에 남겨 처리량 감소를 개선으로 오인하지 않는다. 목표 부하를 유지하지 못한 실행은 사유와 함께 비교 부적합으로 표시한다.

기록 항목은 `시나리오/실행 ID · 코드/정책/모델 버전 · 실제/모의 구간 · 요청 수/속도/동시수/시간 · 중복 조건 · 내부 실행 수 · 응답시간(p50/p95) · 전체 오류율/timeout/거절 · 기한 내 유효 경로 완료율 · 감지/조치/재확인 시각 · 비용 · 최종 결과`다. 반복 횟수와 성공 수치 기준은 W48에서 계측 근거로 확정한다. 11/17 수치는 기획안에 기재된 예비 보고치이며 원본 미대조·오류율 등 미확보 값은 비워 둔다. 모의 지연의 효과를 실제 서비스의 경로/복구 성과로 옮기지 않는다. A1은 B1보다 나은 조치 선택 여부와 추가 판단 시간/비용·잘못 선택한 사례를 함께 보고하고, 개선이 없으면 그대로 적는다.

## 3. 작업 계획표

기간은 계획한 시작일과 완료일이며, ‘선행’에는 먼저 필요한 작업 번호만 표시한다. 선행·연결 작업 번호는 쉼표로 구분한다.

**상태는 ‘할 일 → 진행 중 → 검토 중 → 완료’ 순서로 바꾼다.**

| 상태 | 뜻 |
| --- | --- |
| 할 일 | 아직 시작하지 않은 작업 |
| 진행 중 | 담당자가 작업하고 있는 단계 |
| 검토 중 | 작업 결과를 만들었고, 다른 팀원의 확인이나 제출 확인을 기다리는 단계 |
| 완료 | 필요한 검토와 테스트가 끝난 단계. 제출 작업은 실제 제출 내역까지 확인해야 함 |
| 막힘 | 필요한 자료나 선행 작업을 기다려 진행하지 못하는 상태 |
| 지연 | 계획한 완료일을 넘겼지만 아직 끝나지 않은 상태 |
| 채택 미정 | 추가 작업을 진행할지 아직 정하지 않은 상태. 진행하기로 정하면 ‘할 일’부터 관리 |
| 후속 검토 | Could 기능으로 이번 구현 일정에 배정하지 않은 상태 |

‘막힘’과 ‘지연’은 별도로 표시하는 상황이며, 문제가 해결되면 실제 진행 단계로 바꾼다.

기획서 기준: **Supervisor·Festival·Route·Diagnosis·Recovery 총 5개**, 챗봇은 사용자 UI다. AI는 근거를 해석해 조치를 선택/기각/보류하고, 정책 검사·실행·경로 유효성·결과 판정은 코드가 수행한다. 사건 최종 결과는 `normal_recovered / valid_cache / alternate_source / degraded / unresolved` 5종으로 통일하고 `recovery_action`과 분리한다. `accepted/queued`는 경로 제공 성공이 아니다. 기본 실시간 데이터도 공급원·관측/조회시각·지원 범위를 확인한 경우만 표시한다.
