## WBS 작성 및 일정 관리 원칙

- 작업은 관리 가능한 단위로 나누고, 담당자·기간·선행 관계·산출물·진행 상태를 관리한다.
- 선행 작업의 중간 결과를 먼저 인계받아 착수하는 경우 팀에서 인계 여부를 확인한다.
- **업데이트 주기:** 매주 작업 계획표·실적 기록·간트·제출 관리표를 함께 갱신한다. 담당자가 실제 시작·종료일, 사용 시간, 남은 예상 시간, 결과 링크를 기록하고 검토자가 확인한다. 마감 주에는 매일 점검한다.
- **기능 우선순위:** 기획서의 Must 기능을 우선 구현하며, Should 기능(W39~W43의 통합 찾기 등)은 핵심 기능 개발 상황에 따라 진행하며, 미구현 시 필수 작업의 완료를 막지 않는다. Could 기능은 이번 MVP의 필수 구현 범위에서 제외한다.
- **상태 관리:** `할 일` → `진행 중` → `검토 중` → `완료` 순서로 관리한다. 완료 보고가 있어도 실제 수행일·결과 링크·검토 확인이 없으면 `검토 중`으로 두고, 증빙 확인 후 `완료`로 변경한다. 미착수로 되돌리거나 수행일·실적을 추정하지 않는다. 선행 조건 때문에 착수할 수 없으면 `막힘`, 예정일을 넘겨 미완료이면 `지연`으로 표시하고, 사유 해소 후 해당 진행 단계로 갱신한다. 상태 칸에는 짧은 상태명만 쓰며 상세 사유는 실적 기록에 남긴다.
- **계획·실적 구분:** 간트 차트의 `■`는 계획 기간을 의미하며, 실제 완료 여부는 작업 계획표의 진행 상태로 관리한다.
- **진척률:** `완료가 확인된 필수 작업 수 ÷ 전체 필수 작업 수 × 100`으로 계산한다. 필수 작업은 BFCL을 포함해 82개이며, W85 채택 시 83개가 된다. 선택 작업(W39~W43)은 별도로 집계하고, 범위 변경 시 결정 내용을 기록한다. 현재는 기존 완료 8건의 증빙을 확인한 뒤 진척률을 계산한다.
- **선행 관계:** 선행 작업 완료 후 착수가 원칙이다. 중간 인계로 병행하는 작업은 아래 인계표의 계약·샘플·시점·수신 확인을 충족한 범위만 착수한다. 같은 날 인계는 오전 인계·오후 착수를 계획하며, 미확인 시 해당 범위는 `막힘`으로 기록한다. 인계 목표일은 실제 인계 완료를 의미하지 않는다.
- **지연 관리:** 지연 발생 시 원인, 영향 범위, 변경 예정일을 기록하며, 변경일이 확정되지 않은 경우 `미정`으로 표시한다.

## 이번 주 공수 및 업무 분담 (11/16~11/20)

기존 역할을 유지하면서 R03에 집중된 검증·서버·DB·도구 구현을 분담한다. 아래 시간은 **작업 배정을 위한 최초 계획 추정치**이며 실제 사용 공수나 팀원이 제출한 추정치가 아니다. 실적은 다음 절에 별도로 기록한다. 모든 팀원은 본인 실제 사용 시간·잔여 예상 시간·수업·회의·부재를 제외한 실제 가용 시간을 확인해 아래 표를 갱신한다. 이미 착수했다면 실제 착수 시점도 기록한다. 담당자 확인 전에는 현재 배정의 실행 가능성이 검증된 것으로 보지 않는다.

가용 시간은 비교를 위해 1인당 주 25시간(하루 집중 작업 5시간×5일)을 임시 적용했다. 수업·회의·부재를 확인해 대체하며 초과하면 선택 작업 유예·범위 분할·일정 조정 순으로 해결한다. 작업별 기간을 공수로 합산하지 않는다. R03 검토 시간도 별도 배정한다.

**공수 확정 절차(11/16 첫 점검):** R01은 각 담당자에게 이번 주 실제 가용 시간(수업·회의·부재 제외), 이미 사용한 시간, 작업별 남은 예상 시간을 받는다. `남은 예상 시간 합계 > 남은 실제 가용 시간`이면 차이만큼 넘길 작업·받는 사람·인계 시각을 이 절 아래에 기록하고 작업표의 담당을 함께 고친다. 응답 전에는 아래 25시간을 확정 가용 시간으로 사용하지 않는다. R03의 23시간은 API 설계 6시간, 저장소·인증 정책 4시간, 인증 API 8시간, 계약 검토 4시간, M02 검토 1시간으로 분리해 확인한다. R03의 승인·인증 구현 책임은 유지하고, R04의 실호출 결과, R02의 커넥터·도구 코드, R06의 서버·ERD·DDL은 각 산출물 담당자가 완료·인계한다.
