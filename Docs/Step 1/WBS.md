## 2. 일정 관리 규칙

1. **상태 갱신:** 매주 실제 진행과 결과를 확인해 작업표·간트를 함께 수정한다. 실제 시작·완료일과 결과 링크는 기존 작업 이슈나 회의록에 남긴다. 지연 시 이유와 변경 예정일을 적는다.
2. **완료·제출:** 필요한 검토와 테스트를 통과해야 완료로 표시한다. 실제 API 연결은 임시 데이터만으로 완료 처리하지 않는다. 문서 작성·검토와 실제 제출·접수를 구분해 확인한다.
3. **진행률:** 검토·시험·해당 제출 확인까지 끝난 **필수 완료 수÷103×100**으로 계산한다. 전체 111개 중 선택·조건부·후속 8개(W40·W43·W85·W107·W108·W109·W110·W111)는 분모에서 제외한다. W111 일반 트래픽 고도화와 달리 최소 귀가 부하 재현·계측(W96), 실제 조치 구현·비교 검증(W48~W52·W106)은 필수다. 선택 작업은 12/04까지 채택/미채택/보류와 담당·공수·일정·시험을 함께 결정하고, 필수 승격 시 기준일과 분모 변경을 기록한다. 현재 증빙을 확인하지 못했으므로 확정 완료 수·진행률은 산정 보류한다.
4. **선행·작업량:** 필요한 결과물을 전달받은 뒤 확인한 범위부터 후속 작업을 시작한다. 예상 작업시간·검토 시간·실제로 일할 수 있는 시간은 기존 작업 이슈나 회의록에 기록한다. 일이 몰리면 분담하고, 그 결과를 WBS의 담당·산출물·일정에 반영한다. 전국 플랫폼·귀가 처리·W96·W48~W52가 우선이다. R03·R06의 API/DB·수집·귀가·부하 작업 중첩과 검토 시간을 먼저 확인하고, 후순위 현장/선택 기능은 일정 영향을 확인해 조정한다. 주말 작업·코어타임·부재 사전 공유·회의록/결정 기록 담당은 11/18까지 팀에서 협의하는 계획으로 둔다(R01·R06 정리). 합의 전 주말을 기본 공수에 넣지 않는다.
5. **휴일:** 주말·12/25·01/01을 작업일에서 제외한다. 기본 작업일은 총 38일이며, 추가 휴강·개인 휴가는 확인 후 반영한다. 12/24 배포 이후에는 새 기능보다 문제 수정·재시험·제출 준비에 집중한다.

W48은 12/02 기존 예비 자료로 정책 틀을 준비하고 W96의 12/03 계측 중간본을 받아 구체화한다. 12/04 오전 W48 정책 결정표 초안을 W44에 전달하고, W96의 12/04 기준선·후보 효과 검토본을 확인한 뒤 12/04 오후 W48을 확정해 W44에 다시 전달한다. W44는 12/04에는 초안으로 역할·계약만 준비하고 12/07부터 확정된 정책을 설계에 반영한다. W96 또는 W48 전달이 늦어지면 의존 범위를 막힘으로 표시하고 W44·W45 일정을 재검토한다. 협업 설계(M06)와 복구 시험/결과서(M07)는 같은 장애·성공/중단 기준을 사용한다. 기획안 v2.7의 Supervisor·Festival·Route·Diagnosis·Recovery 5개를 유지한다. 대표 흐름은 Supervisor→Route→Diagnosis→Recovery→코드 실행/검증이며 Festival은 축제 정보가 필요할 때 호출한다. 모든 요청에 5개를 강제 실행하지 않는다. 대표 장애는 내부 귀가 조회 지연·과부하, 혼잡 API는 보조다. 독립 대체 공급원은 실제 확보·검증 시에만 사용한다.

**M02 API·DB 설계서 책임:** R03 권오현이 API 설계서와 DB 스키마 설계서 작성·최종 취합·제출을 맡고, R06 신유빈이 검토한다. W11·W15·W16 설계 초안은 11/19까지 준비하며, 11/20 유빈 검토와 오현 수정·최종 취합 후 제출한다. W98 전국 축제와 W10 실제 귀가 경로 응답을 우선 대조한다. W10은 R04가 팀 키로 원본 요청/응답을 확보하고 R03이 공급원·오류·쿼터·모의 여부를 검토해 M02 API 계약에 반영한다. W95 지원/미지원 기준과 W96 시험 설계 초안을 함께 연결한다. 실호출 실패는 원인·담당·다음 확인일을 적고 모의 응답과 구분한다. 설계 문서 작성/검토 책임은 기존 배정을 유지한다. 변경 기획에 맞춰 W36은 R03 구현·R06 검토, W96은 R06 구현·R04 검토로 배정한 계획이며 팀 작업량 검토 시 조정한다.

## 3. 작업 계획표

기간은 계획한 시작일과 완료일이며, ‘선행’에는 먼저 필요한 작업 번호만 표시한다. 선행·연결 작업 번호는 쉼표로 구분한다.

**상태는 ‘할 일 → 진행 중 → 검토 중 → 완료’ 순서로 바꾼다.**

| 상태 | 뜻 |
| --- | --- |
| 할 일 | 아직 시작하지 않은 작업 |
| 진행 중 | 담당자가 작업하고 있는 단계 |
| 검토 중 | 작업 결과를 만들었고, 다른 팀원의 확인이나 제출 확인을 기다리는 단계 |
| 완료 | 필요한 검토와 테스트가 끝난 단계. 제출 작업은 실제 제출 내역까지 확인해야 함 |
| 막힘 | 필요한 자료나 선행 작업을 기다려 진행하지 못하는 상태 |
| 지연 | 계획한 완료일을 넘겼지만 아직 끝나지 않은 상태 |
| 채택 미정 | 추가 작업을 진행할지 아직 정하지 않은 상태. 진행하기로 정하면 ‘할 일’부터 관리 |
| 후속 검토 | Could 기능으로 이번 구현 일정에 배정하지 않은 상태 |

‘막힘’과 ‘지연’은 별도로 표시하는 상황이며, 문제가 해결되면 실제 진행 단계로 바꾼다.

기획서 기준: **Supervisor·Festival·Route·Diagnosis·Recovery 총 5개**, 챗봇은 사용자 UI다. AI는 근거를 해석해 조치를 선택/기각/보류하고, 정책 검사·실행·경로 유효성·결과 판정은 코드가 수행한다. 사건 최종 결과는 `normal_recovered / valid_cache / alternate_source / degraded / unresolved` 5종으로 통일하고 `recovery_action`과 분리한다. `accepted/queued`는 경로 제공 성공이 아니다. 기본 실시간 데이터도 공급원·관측/조회시각·지원 범위를 확인한 경우만 표시한다.
