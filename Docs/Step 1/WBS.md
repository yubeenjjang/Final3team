## 2. 일정 관리 규칙

1. **상태 갱신:** 매주 실제 진행과 결과를 확인해 작업표·간트를 함께 수정한다. 실제 시작·완료일과 결과 링크는 기존 작업 이슈나 회의록에 남긴다. 지연 시 이유와 변경 예정일을 적는다.
2. **완료·제출:** 필요한 검토와 테스트를 통과해야 완료로 표시한다. 실제 API 연결은 임시 데이터만으로 완료 처리하지 않는다. 문서 작성·검토와 실제 제출·접수를 구분해 확인한다.
3. **진행률:** 필수 계획 103개 중 완료 확인 수÷103×100으로 계산한다. 후기 W40/W43·고급 경로 W107·통합 찾기 W108·주변 상권 W110·트래픽 W111은 Should로 별도 관리한다. W85는 조건부, W109는 후속 Could이며 필수 분모에서 제외한다. 12/04까지 Should 착수 여부·추가공수·일정을 팀이 정하고 필수 승격 시 분모·시험을 함께 수정한다. D12/D14 관리자 기능은 기획안의 Must 제안으로 배정했으며 팀 확정 시 조정한다. 기존 완료 보고는 증빙 확인 후 반영한다.
4. **선행·작업량:** 필요한 결과물을 전달받은 뒤 확인한 범위부터 후속 작업을 시작한다. 예상 작업시간·검토 시간·실제로 일할 수 있는 시간은 기존 작업 이슈나 회의록에 기록한다. 일이 몰리면 분담하고, 그 결과를 WBS의 담당·산출물·일정에 반영한다. 수집·관리자·5개 협업과 추가 작업에 필요한 시간을 함께 확인하기 전에는 일정 실행 가능성이 확정된 것으로 보지 않는다.
5. **휴일:** 주말·12/25·01/01을 작업일에서 제외한다. 기본 작업일은 총 38일이며, 추가 휴강·개인 휴가는 확인 후 반영한다. 12/24 배포 이후에는 새 기능보다 문제 수정·재시험·제출 준비에 집중한다.

## 3. 작업 계획표

기간은 계획한 시작일과 완료일이며, ‘선행’에는 먼저 필요한 작업 번호만 표시한다.

**상태는 ‘할 일 → 진행 중 → 검토 중 → 완료’ 순서로 바꾼다.**

| 상태 | 뜻 |
| --- | --- |
| 할 일 | 아직 시작하지 않은 작업 |
| 진행 중 | 담당자가 작업하고 있는 단계 |
| 검토 중 | 작업 결과를 만들었고, 다른 팀원의 확인이나 제출 확인을 기다리는 단계 |
| 완료 | 필요한 검토와 테스트가 끝난 단계. 제출 작업은 실제 제출 내역까지 확인해야 함 |
| 막힘 | 필요한 자료나 선행 작업을 기다려 진행하지 못하는 상태 |
| 지연 | 계획한 완료일을 넘겼지만 아직 끝나지 않은 상태 |
| 채택 미정 | 추가 작업을 진행할지 아직 정하지 않은 상태. 진행하기로 정하면 ‘할 일’부터 관리 |
| 후속 검토 | Could 기능으로 이번 구현 일정에 배정하지 않은 상태 |

‘막힘’과 ‘지연’은 별도로 표시하는 상황이며, 문제가 해결되면 실제 진행 단계로 바꾼다.

기획안 v2.2 기준: **Supervisor·Festival·Route·Diagnosis·Recovery 정확히 5개**이며 챗봇은 별도 에이전트가 아닌 사용자 화면이다. 혼잡 API 장애가 대표, 목록·LLM·경로 오류는 보조다. 트래픽 급증 대응(FR-H12)은 Should로 W111에서 별도 결정하며, 예매와 관련 Auto-Healing은 이번 MVP에서 제외한다. 인증은 관심·후기·관리자 보호에 필요한 내부 작업으로 유지하고 독립 대표 기능으로 확대하지 않는다.
