# 요청서 — 계약 기반 모의 API 서버 (2026-11-22, 권오현)

## 왜 만드나
- 11/23(월)부터 팀원이 바로 작업을 시작하게 하려고 만든다. 실제 DB·외부 API가 준비되기 전이라도 **API 설계문서 v0.3.3과 같은 주소·같은 형식**으로 답하는 서버가 있어야 한다.
  - 화면(이수언·정예진): 축제 목록·상세·귀갓길 화면을 이 서버에 붙여 본다.
  - 에이전트(한다영): 도구(`search_festivals`·`get_festival`·`request_return_route`·`get_route_request_status`)가 부를 대상으로 쓴다.
- 나중에 실제 구현으로 바꿀 때 **주소와 응답 모양은 그대로 두고 안쪽만** 바꾼다. 따로 버릴 가짜 서버를 만들지 않는다.

## 요청의 말
1. FastAPI로 `backend/api/`에 서버를 띄운다. 주소는 모두 `/api/v1`로 시작한다.
2. 모든 응답에 `is_mock: true`를 넣어, 가짜 데이터라는 것이 화면에서 보이게 한다.
3. 오류는 한 가지 모양 `{"error": {code, message, request_id, retryable}}`으로만 돌려준다. FastAPI 기본 422 모양도 이 모양으로 바꾼다.
4. 요청마다 `X-Request-ID`를 받거나 만들어서 응답 헤더와 오류에 넣는다.
5. 축제 목록(A02)·상세(A03)는 가상 축제 몇 개로 지역·상태·기간·키워드·페이지 필터가 실제처럼 동작해야 한다.
6. 귀갓길(A04)·가는 길(A25)은 출발·도착을 고를 수 있어야 하고, 둘 다 축제 장소면 거부한다.
7. 귀갓길 결과 조회(A05)는 대기 → 처리 중 → 완료처럼 **상태가 바뀌는 흐름**을 흉내 내야 한다. 실패·시간 초과·거절 상태도 시험할 수 있어야 한다.
8. 챗봇(A06)은 질문을 작업으로 받고(202), 결과 조회(A06-1)는 진행 중 → 완료/실패를 흉내 낸다.
9. 회원가입·로그인·토큰 갱신·로그아웃(A32~A35)은 메모리에만 저장하는 가짜로 동작한다(진짜 비밀번호 저장·DB 없음).
10. 다른 팀원의 담당 폴더(`agents/`, `shared/`, `frontend/`, `infra/`, 다른 사람 라우터)는 건드리지 않는다.
11. 누구나 명령 한 줄로 띄우고, 명령 한 줄로 시험할 수 있어야 한다.
12. 외부 API(TMAP·카카오·TourAPI)는 절대 부르지 않는다. 키도 필요 없다.

## 6단계 추가 요청 (2026-11-23, 권오현) — 공급원 구분·오류 시나리오
- 근거: 신유빈 11/23 요청 ④(프론트 연동 정보: 상태·오류 코드, 실제·모의 구분), 강사 11/20 API 피드백 1·2(처리 중·완료·실패 구분, **동기 응답에서만 줄 수 있는 결과(카카오 2차)와 비동기 상태 조회 구분**).
13. 귀갓길 모의 응답에 **2차 공급원(카카오) 결과**를 흉내 내는 경우를 넣는다: 접수 때 바로(200) 답하고, `provider_tier: "secondary"`로 표시한다.
14. 202로 접수된 뒤 1차가 실패하면 2차 결과를 나중에 줄 수 없으므로 `unavailable` + `ROUTE_SECONDARY_SYNC_ONLY`(다시 요청하면 됨)로 답하는 경우를 넣는다.
15. 화면이 오류 문구를 다 만들 수 있게 `ROUTE_NO_RESULT`(경로 없음, 재시도 안 됨)·`ROUTE_QUOTA_EXCEEDED`(한도 소진)도 고를 수 있게 한다.
16. 기존 시나리오·응답·시험은 바꾸지 않는다(추가만).
