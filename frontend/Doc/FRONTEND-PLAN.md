## 1. 개발 목표와 핵심 사용자 흐름

### 1.1 서비스 목표
- 전국 축제 **검색·목록·상세** 제공, 취향 선택에 따른 축제 추천
- 축제에 함께 갈 **동행 모집·신청·채팅** 지원
- 서울 데이터 지원 구역의 **주변 지역 혼잡·현장 정보** 안내
- 공식 통제와 이용 가능성을 고려한 **AI 안심귀가 경로 비교**
- 자연어 질의와 예시 문구로 AI 기능에 접근하는 모바일 우선 경험

### 1.2 우선 시연 흐름
`축제 목록 → 축제 상세 → 주변 혼잡/공식 공지 확인 → AI 안심귀가 → 경로 조회 중 → 경로 후보 비교 또는 확인 불가 안내`

- 백엔드 요청서의 12/8 시연 흐름과 동일하다.
- 유효 경로가 없거나 공식 통제를 확인하지 못한 경우 **경로를 지어내거나 안전을 보장하는 문구를 내보내지 않는다.**
- `queued`, `processing`은 성공이 아니고 `ready`이면서 검증된 후보가 존재할 때만 경로로 표시한다.

### 1.3 회원 온보딩 흐름
`이메일 회원가입 → 최초 취향 선택(선택적 건너뛰기) → 취향 선택 완료 → 맞춤 축제 보기 또는 홈 → 상세`

- 취향은 아래 5개 중 **복수 선택 가능**. 로그인할 때마다 다시 묻지 않는다.
  1. 가족과 한가로운 축제
  2. 친구와 액티비티 축제
  3. 연인과 포토존 즐기는 축제
  4. 애견 동반 축제
  5. 혼자 즐기는 축제
- 프로필/마이페이지에서 취향 변경 가능; 자체 이미지 업로드나 프로필 사진 변경 없음.

## 4. 기술 및 프로젝트 구조

### 4.1 확정/제안 분리
- **확정:** Next.js App Router + React + TypeScript + Tailwind CSS 반응형 웹, FastAPI 내부 API 연동, Git/GitHub 협업, Figma 기반 UI 검토, AWS/Docker 백엔드 환경.
- **현재 구조:** 화면은 `src/app`, 기능은 `src/features`, 공통 API는 `src/lib/api`에 둔다. 기존 프레임워크와 패키지 구조를 유지한다.
- **결정 필요:** 추가 상태관리·데이터 요청 라이브러리 도입 여부와 지도 SDK 확장 방식.
- **인증:** FastAPI 자체 JWT 및 AWS Docker PostgreSQL 기준(기존 API v0.3 문서). Supabase 로그인으로 단정하지 않음.

### 4.2 권장 소스 구조(예시, 확정 아님)
```text
src/
  app/                  # 라우터, 앱 진입, 전역 Provider
  assets/               # 확정 로고, 승인된 기본 이미지
  styles/               # tokens.css, global.css, typography.css
  components/
    layout/              # Header, BottomNavigation, PageContainer
    ai/                  # AIQuestionBar, ExampleChips
    festival/            # FestivalCard, FestivalCarousel, FestivalSection
    route/               # SafeReturnBanner, RouteCard, RouteStatus
    common/              # Loading, Empty, Error, Toast, Badge
  features/
    auth/ onboarding/ home/ festivals/ companions/ chat/ return/ map/ mypage/
  services/              # API 클라이언트 및 도메인별 호출
  hooks/                 # 재사용 상태/조회 로직
  types/                 # API 타입과 화면 모델
  utils/                 # 날짜/KST, 상태 매핑, 입력 검증
```

### 4.3 구현 품질 원칙
1. **API 응답 모양을 화면에서 추측하지 않는다.** 문서/Swagger/실제 샘플로 확인한다.
2. 모든 데이터 영역은 `loading / success / empty / unavailable / error`를 정의한다.
3. 서울 혼잡 정보가 없는데 다른 지역 데이터로 대신 표시하지 않는다.
4. 공식 통제/무정차 정보를 위반하는 귀가 경로를 화면에서 추천하지 않는다.
5. `is_mock=true`이면 실제 정보로 오인되지 않도록 **시연/예시**를 표시한다.
6. 토큰, 외부 API 키, 위치 등 민감 데이터는 브라우저 로그·URL에 남기지 않는다.

## 5. 반응형/접근성 기준

- 기본 시안 **390px**. 기준 검증 너비: 320, 360, 390, 430, 768, 1024, 1440px.
- 모바일 본문 세로 길이는 자동. 하단 탭 고정 시 `safe-area-inset-bottom`과 본문 아래 패딩을 함께 적용한다.
- 390px에서는 3.5개 카드가 보이도록 하되, **360px 미만에서 글자가 지나치게 작아지면 2.5개로 단계 전환 가능**(디자인 승인 필요).
- 터치 영역 44×44 CSS px 이상 권장, 스와이프뿐 아니라 키보드/버튼으로 카드 이동 가능하게 구성.
- 텍스트 대비, 대체 텍스트, 로딩 상태의 `aria-live`, 포커스 표시 등을 확인한다.
- `prefers-reduced-motion`을 고려하고 불필요한 과도한 애니메이션을 피한다.

## 6. 백엔드 상태 UI — 필수 A1~A12

| ID | 화면 상태 | 완료 화면 조건 |
|---|---|---|
| A1 | 포스터 이미지 없음 | 로고 + '이미지 준비 중' 카드/상세 변형 2종 |
| A2 | 혼잡 4단계 | **주변 지역 혼잡**, 여유/보통/약간 붐빔/붐빔, 퍼센트 제거 |
| A3 | 혼잡 구역 최대 3개 | 이름·단계·거리 표시 |
| A4 | 관측 시각/오래됨/지역 미지원 | '16:40 기준', 45분 경과 시 오래됨, 서울 밖 안내 |
| A5 | 귀가 처리 중 | 대기열/처리 중 진행 표시 |
| A6 | 경로 조회 불가/시간 초과 | 재시도와 공식 안내 이동 |
| A7 | 막차 종료 | 이용 가능한 경로 없음 문구 |
| A8 | 카카오 대체 경로 | 막차 확인 불가 표시(값 없을 때만) |
| A9 | 경로 지도 출처 | '경로 정보: TMAP' 등 실제 공급원 표시 |
| A10 | 경로 선택 유형 | 가장 빠른 / 도보 최소 / 환승 최소 / 혼잡 적은 / 이동 편한 |
| A11 | 429·503 과부하 | 짧은 오류 토스트 |
| A12 | 축제 빈 목록/404 | 빈 결과 화면과 재검색 동선 |

추가 B1~B8은 백엔드 요청서의 **후순위 작업**. 단, B1의 '관심 하트'는 제외 기능과 충돌하므로 디자인에 넣지 않는다. 상세 '주요 프로그램'·해시태그 데이터가 없으면 해당 영역은 숨긴다.
